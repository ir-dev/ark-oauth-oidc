Security review

Security review — 20 November 2026

A full review of the ARK identity provider and its four client libraries, prompted by applications now using ARK for customer-facing sign-in. It combined automated scanning, a manual code review of every endpoint and library, and live attack tests against running providers. Every high-impact finding was confirmed against a running provider, fixed, and tested again. The rest are listed with mitigations.

What operators need to do

Upgrade every ARK identity provider and every application that uses an ARK client library to v2.2.0 or later. The fixes change some behaviour, and these are the changes you will notice.

On the identity provider

  1. Everyone signs in once more after the upgrade. The single sign-on cookie has a new format, so sessions from before the upgrade are not recognised.
  2. Set a real DefaultPw, or use UserPasswordMode=email_based. Creating an account with the default password unset, or still set to a <<placeholder>> value, now fails with 409 default_password_unset.
  3. The legacy onboard/* routes accept only the machine client's bearer token and never change an existing account. Use the provisioning API (v1/provision/*) for new integrations.
  4. Set BaseUrl and restrict AllowedHosts on every production host. Behind a TLS-terminating proxy, enable forwarded headers (on App Service: ASPNETCORE_FORWARDEDHEADERS_ENABLED=true).
  5. Rate limiting: until the provider has its own, put the sign-in, token, PAR, device and registration endpoints behind rate limiting at your edge (see O2).

In applications

  • .NET APIs using AddArkOidcApi accept only access tokens (typ: at+jwt). If you use a provider that does not mark its access tokens this way, set RequireAccessTokenTypeHeader=false.
  • .NET apps no longer serve the legacy /oauth/{tenant}/v1/client/… routes unless ark_oauth_client:UseLegacyFlow is set. The legacy /config route is removed entirely.
  • Python / Flask session cookies are now Secure by default, as the documentation already said. Pass cookie_secure=False only for a plain-http host other than localhost.
  • APIs should authorise by Ark claims and check the caller's client_id, not only that the token is valid (see O5).

How the review was done

Scanners find the known-bad patterns. Most of what mattered here, though, is logic that scanners cannot see. Every issue below was found by reading the code, and every high-severity one was then confirmed against a running provider.

Automated scanning

  • Dependencies: dotnet list package --vulnerable, npm audit, pip-audit. No known vulnerabilities.
  • Static analysis: Semgrep (586 rules), Bandit, .NET security analyzers. No actionable findings, before or after the fixes.
  • Secrets: gitleaks over the full history and the working tree. Nothing beyond test fixtures and previously documented history.

Manual review and live tests

  • Code review of the authorization, token, PAR, device, registration, introspection, revocation, logout and userinfo endpoints; the management API, admin console and setup wizard; and all four client libraries.
  • Live attacks against three scratch providers (two configured hosts and one zero-config QuickStart), all running in Production mode.
  • After the fixes: 46 live checks pass, covering both refused attacks and unchanged legitimate flows. The client suites pass too: Python 132, Node 135, browser 115.

Fixed findings

Described at the level an operator needs. Reproduction details are left out on purpose.

ARK-01CriticalFixed

Single sign-on session takeover from any issued token

Issue
The browser's single sign-on cookie held the same value as the sid claim in every ID token, access token, introspection response and logout token.
Impact
Anyone who saw one of a user's tokens could use it to sign in as that user at every application in the tenant, without a password. That includes any relying party, any API that receives access tokens, a device the user approved, or a log. In the operator tenant, that extends to the admin console.
Fix
The cookie is now a random secret. The session identifier carried in tokens is its one-way hash, so holding a token no longer lets anyone produce the cookie. Sessions created before the upgrade are not recognised.
ARK-02HighFixed

Codes and refresh tokens redeemable at another tenant

Issue
A client_id is unique within a tenant only, but authorization codes, refresh tokens, device codes and pushed requests were checked against the client_id alone.
Impact
Where two tenants register a client under the same id, a user of one tenant could obtain tokens signed by the other tenant, which accepted them, without having any access there.
Fix
Every grant is now checked against both tenant and client: code, refresh, device and PAR redemption, and refresh-token introspection and revocation.
ARK-03HighFixed

Legacy onboarding routes could reset any password, via a link or a sign-up form

Issue
Two legacy onboarding routes accepted any HTTP verb and authenticated through the admin console's cookie. They also overwrote an existing account's password and reactivated it.
Impact
An operator who followed a crafted link from another site could have any account's password set, their own included. Separately, an application that wired its public sign-up form to the onboarding helper let anyone take over an existing account by signing up with its address.
Fix
Both routes accept only the machine client's bearer token, which a cross-site page cannot attach. Onboarding never changes an existing account.
ARK-04HighFixed

Stored cross-site scripting through a registered client name

Issue
Some admin-console grid cells inserted registration data, such as a client's display name, as HTML.
Impact
Whoever could register a client could run script in the operator's console session, with the operator's authority.
Fix
Every console formatter now escapes its output, and so does the legacy console view. Dynamic registration also rejects markup and control characters in client_name.
ARK-05HighFixed

Legacy controller exposed the client secret and stack traces (.NET client)

Issue
Every MVC application referencing Ark.oAuth.Client served the v1 controller, whether or not the legacy flow was used. Its configuration route was open to any signed-in user, and its callback printed exception details.
Impact
Any signed-in user, every customer of a customer-facing app included, could read the application's client secret. Anonymous visitors could see server stack traces.
Fix
The legacy routes exist only when UseLegacyFlow is set. The configuration route is removed, and errors are logged instead of displayed.
ARK-06HighFixed

private_key_jwt clients accepted without their key

Issue
A client registered for private_key_jwt has no stored secret, so the provider treated it as a public client.
Impact
The token, PAR and revocation endpoints accepted such a client with nothing but its id. Its codes and refresh tokens could be redeemed without the private key it was registered to prove.
Fix
A private_key_jwt client is confidential and must present a valid signed assertion.
ARK-07HighFixed

New accounts created on a published placeholder password

Issue
The sample configuration ships DefaultPw as a <<placeholder>>. The administrator seed refused that value, but account creation used it as-is.
Impact
On a host left on the sample value, every account created in the console or through provisioning signed in with a password published in the repository.
Fix
An empty or placeholder DefaultPw is refused before anything is written (409 default_password_unset). Accounts awaiting email activation start on a random, unusable password.
ARK-08HighFixed

API validation accepted ID tokens as access tokens (.NET client)

Issue
AddArkOidcApi did not check the token type, and by default it does not check the audience either.
Impact
An ID token, which any single-page app holds, was accepted as a bearer token by .NET APIs protected only by [Authorize]. The Node and Python libraries already refused this.
Fix
Only typ: at+jwt tokens are accepted by default, matching the other libraries. RequireAccessTokenTypeHeader=false turns the check off.
ARK-09MediumFixed

Refresh tokens kept working after a user's access was removed

Impact
Taking a user off an application stopped new sign-ins, but their existing refresh tokens kept issuing access tokens until the session expired, eight hours by default.
Fix
The refresh grant re-checks the user's access to the client and revokes the token family when it is gone.
ARK-10MediumFixed

A removed operator kept console rights for the life of the session

Impact
In the zero-config host, the console session renewed on every request and operator status was read from sign-in claims. Deactivating an operator, removing their console access or taking away their admin claim changed nothing for a session already open.
Fix
Every console request re-checks the account, its console mapping and its admin claim against the database.
ARK-11MediumFixed

Account enumeration through sign-in messages and lockout

Impact
The legacy v1 sign-in page used different messages for an unknown account, an account without access and a wrong password. On both sign-in pages, the lockout message appeared only for accounts that exist.
Fix
Both pages show one message for every credential failure, and every failure, for any username, counts towards the lockout.
ARK-12MediumFixed

Logout confirmation bypass (forced sign-out)

Impact
Any valid ID token for the tenant skipped the logout confirmation, even one belonging to someone else. A page could sign a visitor out of every application, in every tenant on that browser.
Fix
A hint skips the confirmation only when it names a session being ended. A client_id sent alongside the hint must be one the hint was issued to.
ARK-13MediumFixed

Tenant update returned the private signing key

Impact
The management API's tenant update returned the tenant's live private signing key to the console's browser.
Fix
The response no longer contains private key material.
ARK-14MediumFixed

Client-credentials token cache ignored the secret (.NET, Python)

Impact
Once a token was cached, the right client_id with any secret received it. A secret-check step could pass for a secret the provider would refuse.
Fix
The cache key now includes a hash of the credential, as the Node library already did.
ARK-15MediumFixed

Flask session cookie not Secure by default (Python client)

Impact
Flask pre-sets SESSION_COOKIE_SECURE=False, so the intended secure default never took effect. The session cookie could travel over plain http.
Fix
The cookie is Secure unless the application passes cookie_secure=False.
ARK-16MediumFixed

Unbounded pushed requests; expired state never purged

Impact
The PAR endpoint stored whatever a public client posted, and expired codes, sessions and pushed requests were never deleted. Storage could grow without limit.
Fix
Pushed requests are capped at 50 parameters and 16 KB. A background job deletes expired state hourly (Oidc:CleanupIntervalMinutes; 0 disables it).
ARK-17MediumFixed

User identity read from browser-supplied legacy cookies (.NET client)

Impact
The request context read the user id, IP address and claims from v1 cookies even under the standard flow, so an anonymous request could name its own identity to code that records who did what.
Fix
Those cookies are read only under UseLegacyFlow, and the IP address comes from the connection.
ARK-18MediumFixed

Setup code skipped for proxied or rebound requests

Impact
On an unconfigured provider, the setup wizard skipped its one-time code for loopback connections. A same-host proxy that adds no forwarding header, or a DNS-rebinding page, could therefore complete setup and become the operator.
Fix
The no-code path also requires the request to be addressed to localhost or a loopback address.
ARK-19LowFixed

Five smaller hardening fixes

Fixes
  • Dynamic registration refuses a client_id equal to a user's login id, so a machine token can no longer carry a user's subject.
  • Server-side fetches of client JWKS and back-channel logout no longer follow redirects, and responses are size-capped.
  • Management tokens from the machine client must come from client_credentials.
  • The device-approval and logout-confirmation pages set frame-ancestors explicitly.
  • The .NET onboarding helper URL-encodes every value.

Open items and mitigations

These need a product decision or a deployment control rather than a code fix. Until they are addressed, apply the mitigation.

O1HighOpen

Provisioned accounts share an initial password

Issue
Outside email activation, new accounts start on the configured DefaultPw and are not required to change it.
Mitigation
For customer-facing accounts, use UserPasswordMode=email_based so each person sets their own password from an activation link. Otherwise, set passwords per user in the console. A forced change at first sign-in is planned.
O2MediumOpen

No built-in rate limiting

Issue
Per-account lockout exists, but nothing limits requests per address. Each password or client-secret check is deliberately expensive (PBKDF2), so a modest request rate can exhaust a small instance.
Mitigation
Rate-limit POST /{tenant}/oauth2/authorize, /token, /par, /device_authorization and /register at the edge (WAF, gateway or reverse proxy).
O3MediumOpen

No server-side password policy

Mitigation
Until a minimum length and a breached-password check are enforced, communicate a password policy to users, and prefer email activation so passwords are chosen by their owners.
O4MediumOpen

Confidential clients with no secret behave as public

Mitigation
A client registered for client_secret_basic or client_secret_post but without a secret is treated as a public client and relies on PKCE alone. Give every confidential client a secret (regenerate it in the console), or register it deliberately as none.
O5MediumOpen

One access-token audience per tenant

Mitigation
Access tokens carry the tenant's audience, whichever application they were issued to. APIs should authorise by Ark claims (require_claims / requiredClaims) and check the token's client_id, not only that the token is valid.
O6–O9LowOpen

Host header, server-side fetches, console CSP, client-library defaults

Items
  • O6: with BaseUrl unset, the Host header shapes the issuer and the console's configuration. Always set BaseUrl and restrict AllowedHosts.
  • O7: server-side fetches (client JWKS, back-channel logout) do not block private network ranges. Restrict egress from the provider.
  • O8: admin-console pages have no Content-Security-Policy, and a third-party grid script is loaded without Subresource Integrity.
  • O9: client-library defaults: logout by GET without a CSRF check (Node, Python); .NET silent refresh does not update roles; access-denied page framing (Python, .NET); trust-proxy on by default (Node, Python).
