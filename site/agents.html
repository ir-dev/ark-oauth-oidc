When an AI agent calls another agent, an MCP server, or this identity provider itself, the one being called needs three answers: which agent is this, who is it for, and was this token meant for me? This page draws how ARK answers them, hop by hop. The tokens, replies and refusals shown were recorded from a running server, and the last sections say plainly what ARK does not do.

A2A’s own documentation puts the difference this way: “A2A connects the agents to each other; MCP connects each agent to its own tools” (A2A and MCP). ARK issues the same kind of ticket for both.

The idea

Three questions, answered inside the ticket.

A ticket is a signed access token (a JWT). The receiver reads it without calling anyone. This one was issued to the planner for Alice, to use at the ledger.

"aud": "ledger"
Was this meant for me? The one door it opens. The ledger compares it with its own name.
"sub": "alice@example.com"
Who is it for? The person whose errand this is. When an agent works alone, its own name is here instead.
"act": { "sub": "planner", "act": { "sub": "team-portal" } }
Which agent is this? Everyone Alice was handed through, newest first. She is carried, never impersonated.
"ark_claims": ["orders.read"]
What may it do? Alice’s own rights at the ledger, decided by the operator. An agent cannot add to them.
"exp": no later than the token it came from
For how long? Five minutes at most by default, and never longer than the ticket before it. There is no refresh token.
"sid": "nj0znPrh0JNY…"
From which sign-in? When Alice’s session ends, no further ticket is printed from it.

The server also lists the identity claim names it released (sub, name, email, email_verified) in ark_claims for a person. They are left out on this page for width, along with iss, iat, nbf, jti and scope.

Flow 1 · agent to agent

The agent being called decides who may call it.

An agent is an ordinary confidential client. Nothing about it is special until another client lists it as a caller. Step through the diagram, or press a number on it.

For a person

  1. 1Alice signs in to an ordinary app.

    A standard browser sign-in with PKCE. Her token stays in the portal’s server-side session. It is addressed to the tenant, so every agent and MCP server on this page refuses it.

    her sign-in token
    {
  "aud": "https://idp.example.com/acme/api",
  "sub": "alice@example.com",
  "client_id": "team-portal",
  "sid": "nj0znPrh0JNY…",
  "ark_claims": ["portal.use"]
}

  2. 2The portal asks for a ticket to the planner.

    It proves who it is, shows Alice’s token, and names one target. This is OAuth token exchange (RFC 8693). Nothing is forwarded to the agent yet.

    request
    POST /acme/oauth2/token
Authorization: Basic team-portal:•••

grant_type=urn:ietf:params:oauth:grant-type:token-exchange
subject_token=<Alice’s sign-in token>
subject_token_type=urn:ietf:params:oauth:token-type:access_token
audience=planner

  3. 3ARK checks, then prints a ticket for that one door.

    The ticket still names Alice, because it is her errand. act records that the portal is acting for her. What it allows is what Alice may do at the planner, not what the portal may do.

    ticket
    {
  "aud": "planner",
  "sub": "alice@example.com",
  "client_id": "team-portal",
  "act": { "sub": "team-portal" },
  "ark_claims": ["planner.use"],
  "sid": "nj0znPrh0JNY…"
}

  4. 4The portal calls the planner.

    An ordinary HTTP call with an Authorization: Bearer header, which is where A2A says identity belongs. The call goes straight from app to agent and does not pass through ARK.

    call
    POST https://planner.example.com/a2a/tasks
Authorization: Bearer <the planner ticket>

  5. 5The planner needs the ledger, so it asks for its own ticket.

    It presents the ticket it was sent. Only the agent a ticket is addressed to may do this: the same request from any other client is refused.

    request
    POST /acme/oauth2/token
Authorization: Basic planner:•••

grant_type=urn:ietf:params:oauth:grant-type:token-exchange
subject_token=<the planner ticket>
subject_token_type=urn:ietf:params:oauth:token-type:access_token
audience=ledger

  6. 6The second ticket carries the whole chain.

    act grows by one, newest first. ark_claims are now Alice’s rights at the ledger. It expires no later than the ticket it came from: in the recorded run, one second earlier.

    ticket
    {
  "aud": "ledger",
  "sub": "alice@example.com",
  "client_id": "planner",
  "act": { "sub": "planner",
           "act": { "sub": "team-portal" } },
  "ark_claims": ["orders.read"],
  "sid": "nj0znPrh0JNY…"
}

  7. 7The planner calls the ledger.

    Same call shape. The planner cannot use this ticket anywhere else, and the ledger cannot use the planner’s.

    call
    POST https://ledger.example.com/a2a/tasks
Authorization: Bearer <the ledger ticket>

  8. 8The ledger decides for itself.

    It checks the signature against ARK’s published keys, the issuer, the type, the expiry and that aud is its own name. Then it decides on ark_claims, and reads act to see which agents brought Alice here.

    guard · Python
    @app.post("/a2a/tasks")
@agent.require(claims=["orders.read"])
def tasks():
    current_ark.sub      # alice@example.com
    current_ark.actors   # ["planner", "team-portal"]

As itself

  1. 1The planner asks in its own name.

    For a scheduled job, or any work with no person behind it. A client secret or a signed JWT (private_key_jwt) proves who is asking.

    request
    POST /acme/oauth2/token
Authorization: Basic planner:•••

grant_type=client_credentials
audience=ledger

  2. 2ARK looks at the ledger’s list, not the planner’s.

    The client being called names its callers and what each holds there. An empty list, which is how every client starts, means nobody. The same refusal covers a client that does not exist, so the list cannot be probed.

    ticket
    {
  "aud": "ledger",
  "sub": "planner",
  "client_id": "planner",
  "ark_claims": ["orders.read"],
  "exp": iat + 300
}

  3. 3The planner calls the ledger.

    With a client library, asking, caching and renewing is one call.

    call · Python
    token = ark.agent_token("ledger").access_token

  4. 4The ledger verifies and decides.

    There is no act claim, because nobody is being acted for. sub is the agent itself, and it holds only what the ledger granted it.

    guard · Node
    const agent = arkBearer({ authority, clientId: 'ledger', agent: true });
app.post('/a2a/tasks', agent, agent.require({ claims: ['orders.read'] }), handler);
What ARK checks before it prints a ticket for a person, in order, and the error when it fails
  1. 1Caller proves who it isinvalid_client
  2. 2Registered for this grantunauthorized_client
  3. 3Token is genuine and liveinvalid_grant
  4. 4…and this caller’s to useinvalid_grant
  5. 5Live person and sessioninvalid_grant
  6. 6At most 4 agents deepinvalid_grant
  7. 7Target lists the callerinvalid_target
  8. 8Person has access thereinvalid_target
What the receiver checks, without calling ARK
  1. ASigned by this issuer401
  2. BAccess token, not expired401
  3. CAddressed to me401
  4. DClaim for this action403 or tool error

In its own name, an agent meets checks 1, 2 and 7. None of these rely on what the calling agent says about itself.

Set it up, in the admin console

  1. Give each agent a client with the client_credentials grant, and token-exchange for those that act for people.
  2. Open the client being called, find Agent-to-agent (A2A), press Add calling client, choose the caller, the claims it holds there, and whether it may act for users.
  3. For people, map the person to the target, as for any application.

Full reference: A2A.md, with the API form of the list and one-line guards for .NET, Python and Node. ARK also writes the security section of your Agent Card, at {issuer}/a2a/agent-card-security.

Flow 2 · agent to MCP server

An MCP server is one more door with its own name.

The MCP authorization specification asks for a token issued for that server and nobody else. That is what an ARK ticket is. Three cases: an agent alone, an agent for a person, and a server that calls onward.

As itself, by discovery

  1. 1The MCP client knocks without a ticket.

    This is the official Python MCP SDK with its client-credentials provider, and no ARK code in the client. The server’s refusal tells it where to look.

    recorded
    POST https://mcp.example.com/mcp

401 Unauthorized
WWW-Authenticate: Bearer error="invalid_token",
  resource_metadata="https://mcp.example.com/.well-known/oauth-protected-resource/mcp"

  2. 2The MCP server says who protects it.

    Protected resource metadata (RFC 9728). The MCP SDKs serve it from two settings: the issuer and the server’s own address.

    recorded
    GET /.well-known/oauth-protected-resource/mcp

{ "resource": "https://mcp.example.com/mcp",
  "authorization_servers": ["https://idp.example.com/acme"],
  "scopes_supported": ["profile"] }

  3. 3The client finds ARK’s metadata.

    MCP clients must try three addresses, in this order, for an issuer with a path. ARK answers the third. It advertises S256, which MCP clients insist on.

    recorded
    404  /.well-known/oauth-authorization-server/acme
404  /.well-known/openid-configuration/acme
200  /acme/.well-known/openid-configuration

  4. 4It asks for a ticket, naming the server by its address.

    MCP clients send the server’s address as resource (RFC 8707). ARK reads it as the target’s client_id, so the MCP server is registered under its own address.

    recorded
    POST /acme/oauth2/token

grant_type=client_credentials
client_id=planner&client_secret=•••
resource=https://mcp.example.com/mcp
scope=profile

  5. 5It calls the tool.

    The SDK keeps the ticket and asks again when it runs out. There is no refresh token to steal.

    ticket
    {
  "aud": "https://mcp.example.com/mcp",
  "sub": "planner",
  "client_id": "planner",
  "ark_claims": ["catalog.read"],
  "scope": "profile"
}

  6. 6The server checks the name on the ticket.

    MCP requires a server to accept only tokens issued for it. Here that is one comparison: aud against its own address. Then the tool checks the claim.

    recorded result
    { "for": "planner", "acting": [], "hits": ["x"] }

For a person

  1. 1The planner brings Alice along.

    It was called with a ticket for Alice (flow 1, step 4). It exchanges that ticket for one addressed to the MCP server. To ARK, an MCP server is one more client.

    client library · Python
    token = ark.agent_token("orders-mcp", subject_token=incoming).access_token

  2. 2The ticket holds Alice’s rights at that server.

    The operator mapped her to the Orders server with two claims, and those are what the ticket carries. The planner’s own grant there is smaller and is not mixed in.

    ticket
    {
  "aud": "orders-mcp",
  "sub": "alice@example.com",
  "client_id": "planner",
  "act": { "sub": "planner",
           "act": { "sub": "team-portal" } },
  "ark_claims": ["orders.read", "orders.refund"]
}

  3. 3The planner calls the tool.

    Any MCP client can send it: the ticket is an ordinary bearer header.

    call · Python
    async with httpx2.AsyncClient(headers={"Authorization": f"Bearer {token}"}) as http:
    async with Client(streamable_http_client(url, http_client=http)) as mcp:
        await mcp.call_tool("refund", {"order": "A-1"})

  4. 4The tool checks the claim and knows both names.

    It runs because Alice may refund, and it can record that the planner did it for her.

    recorded result
    { "refunded": "A-1", "by": "alice@example.com",
  "acting": ["planner", "team-portal"] }

  5. 5Without Alice, the planner may only read.

    Calling in its own name, the planner holds what the Orders server granted it: orders.read. The same tool refuses.

    recorded
    ticket  { "aud": "orders-mcp", "sub": "planner", "ark_claims": ["orders.read"] }
reply   Error executing tool refund

The server calls onward

  1. 1A tool needs something from another agent.

    The Orders server holds a ticket for Alice addressed to orders-mcp.

    ticket
    {
  "aud": "orders-mcp",
  "sub": "alice@example.com",
  "act": { "sub": "planner",
           "act": { "sub": "team-portal" } }
}

  2. 2Passing the ticket along does not work.

    MCP forbids token passthrough. Here it is also useless: the ledger reads the name on the ticket and refuses.

    recorded
    the token is addressed to 'orders-mcp', not to 'ledger'.

  3. 3It exchanges the ticket for its own.

    Allowed only because the ledger lists orders-mcp as a caller that may act for users. Before it did, the same request was refused with invalid_target.

    ticket
    {
  "aud": "ledger",
  "sub": "alice@example.com",
  "client_id": "orders-mcp",
  "act": { "sub": "orders-mcp",
           "act": { "sub": "planner",
                    "act": { "sub": "team-portal" } } },
  "ark_claims": ["orders.read"]
}

  4. 4The ledger sees the full path.

    Three names deep, newest first. Four is the limit by default, so a loop between agents ends.

    recorded, the fifth agent
    400 invalid_grant
the delegation chain is too long: 5 agents, and at most 4 are allowed.

The MCP server, complete

Each of these was run as printed, with only the host names changed, and met six tokens: two good ones (the agent alone, and for Alice) and four bad ones (another server’s ticket, a sign-in token, an ID token, an edited ticket). All three answered all six correctly.

Python

server.py · mcp 2.3.0, ark-oauth-client
import asyncio
from mcp.server.mcpserver import MCPServer
from mcp.server.mcpserver.exceptions import ToolError
from mcp.server.auth.provider import AccessToken
from mcp.server.auth.settings import AuthSettings
from mcp.server.auth.middleware.auth_context import get_access_token
from ark_oauth_client import ArkOAuthClient, agent_actors

AUTHORITY = "https://idp.example.com/acme"
URL = "https://mcp.example.com/mcp"        # this server's address, and its client_id in ARK
ark = ArkOAuthClient(authority=AUTHORITY, client_id=URL)

class ArkTokens:
    async def verify_token(self, token):
        try:                               # signature, issuer, typ, expiry, and aud == URL
            p = await asyncio.to_thread(ark.verify_agent_token, token)
        except Exception:
            return None                    # the SDK answers 401 and says where to get a token
        return AccessToken(token=token, client_id=p["client_id"], subject=p["sub"], claims=p,
                           scopes=p.get("scope", "").split(), expires_at=p["exp"])

mcp = MCPServer("catalog", token_verifier=ArkTokens(), auth=AuthSettings(
    issuer_url=AUTHORITY, resource_server_url=URL,
    required_scopes=["profile"],           # a scope your callers hold; permissions are ark_claims
    validate_token_resource=False))        # verify_agent_token has already checked the audience

@mcp.tool()
def search(q: str) -> dict:
    """Search the catalogue."""
    t = get_access_token()
    if "catalog.read" not in t.claims.get("ark_claims", []):
        raise ToolError("needs catalog.read")  # allowed in, not allowed to do this
    return {"for": t.subject, "acting": agent_actors(t.claims), "hits": [q]}

app = mcp.streamable_http_app()            # uvicorn server:app

using Ark.oAuth;
using Microsoft.AspNetCore.Authentication.JwtBearer;
using ModelContextProtocol.AspNetCore.Authentication;
using ModelContextProtocol.Server;

const string Authority = "https://idp.example.com/acme";
const string Url = "https://mcp.example.com/mcp";    // this server's address, and its client_id in ARK

var builder = WebApplication.CreateBuilder(args);
builder.Services.AddAuthentication(o =>
    {
        o.DefaultAuthenticateScheme = JwtBearerDefaults.AuthenticationScheme;
        o.DefaultChallengeScheme = McpAuthenticationDefaults.AuthenticationScheme; // 401 + resource_metadata
    })
    .AddArkAgentApi(new ArkAuthConfig { Authority = Authority, ClientId = Url })   // aud must be Url
    .AddMcp(o => o.ResourceMetadata = new()
    {
        Resource = Url,
        AuthorizationServers = { Authority },
        ScopesSupported = ["profile"]                // a scope your callers hold; permissions are ark_claims
    });
builder.Services.AddAuthorization();
builder.Services.AddHttpContextAccessor();
builder.Services.AddMcpServer().WithHttpTransport(o => o.Stateless = true).WithTools<CatalogTools>();

var app = builder.Build();
app.UseAuthentication();
app.UseAuthorization();
app.MapMcp("/mcp").RequireAuthorization(p => p.RequireClaim("ark_claims", "catalog.read"));
app.Run();

[McpServerToolType]
public class CatalogTools(IHttpContextAccessor http)
{
    [McpServerTool(Name = "search")]
    public object Search(string q)
    {
        var user = http.HttpContext!.User;
        return new { @for = user.FindFirst("sub")?.Value, acting = user.ArkActors(), hits = new[] { q } };
    }
}

Node

server.mjs · @modelcontextprotocol/sdk 1.32.2, ark-oauth-client-node
import express from 'express';
import { McpServer } from '@modelcontextprotocol/sdk/server/mcp.js';
import { StreamableHTTPServerTransport } from '@modelcontextprotocol/sdk/server/streamableHttp.js';
import { requireBearerAuth } from '@modelcontextprotocol/sdk/server/auth/middleware/bearerAuth.js';
import { InvalidTokenError, InsufficientScopeError } from '@modelcontextprotocol/sdk/server/auth/errors.js';
import { ArkOAuthClient, agentActors } from 'ark-oauth-client-node';
import { z } from 'zod';

const AUTHORITY = 'https://idp.example.com/acme';
const URL = 'https://mcp.example.com/mcp';   // this server's address, and its client_id in ARK
const METADATA = '/.well-known/oauth-protected-resource/mcp';
const ark = new ArkOAuthClient({ authority: AUTHORITY, clientId: URL });

const bearer = requireBearerAuth({
  resourceMetadataUrl: 'https://mcp.example.com' + METADATA,
  verifier: {
    async verifyAccessToken(token) {         // signature, issuer, typ, expiry, and aud === URL
      const p = await ark.verifyAgentToken(token, { arkClaims: ['catalog.read'] })
        .catch(e => { throw new (e.error === 'insufficient_scope' ? InsufficientScopeError : InvalidTokenError)(e.message); });
      return { token, clientId: p.client_id, scopes: (p.scope ?? '').split(' '), expiresAt: p.exp,
               extra: { sub: p.sub, actors: agentActors(p) } };
    }
  }
});

const app = express();
app.get(METADATA, (_req, res) => res.json({
  resource: URL, authorization_servers: [AUTHORITY],
  scopes_supported: ['profile']              // a scope your callers hold; permissions are ark_claims
}));
app.post('/mcp', express.json(), bearer, async (req, res) => {
  const server = new McpServer({ name: 'catalog', version: '1.0.0' });
  server.registerTool('search', { inputSchema: { q: z.string() } }, ({ q }, { authInfo }) => ({
    content: [{ type: 'text', text: JSON.stringify({ for: authInfo.extra.sub, acting: authInfo.extra.actors, hits: [q] }) }]
  }));
  const transport = new StreamableHTTPServerTransport({ sessionIdGenerator: undefined });
  await server.connect(transport);
  await transport.handleRequest(req, res, req.body);
});
app.listen(3000);

Register the server under its own address

MCP clients name the server by URL, and ARK looks the name up as a client_id. Type the exact address, for example https://mcp.example.com/mcp, as the client_id in the console or through the management API. A short id such as orders-mcp works too when your own code asks for the ticket; an unmodified MCP client gets invalid_target.

Publish a scope your callers hold

MCP clients request whatever the server lists in scopes_supported, and ARK refuses a scope the calling client is not registered for. If the server lists none, the Python SDK asks for everything ARK knows, which is refused too. List one they hold, such as profile, and keep permissions in ark_claims.

Flow 3 · agent to the IdP, through MCP

The agent gets tools. The operator credential stays behind them.

ARK’s management API can create clients, map people to applications and switch accounts off, across every tenant. No agent should hold the key to that. Put a small MCP server in front: it is a door like any other, and it alone holds the key.

  1. 1The agent asks for a ticket to the gateway.

    The gateway is a client like any other, so the operator lists the planner as its caller and maps Alice to it with the claims she should have there.

    ticket
    {
  "aud": "idp-mcp",
  "sub": "alice@example.com",
  "client_id": "planner",
  "act": { "sub": "planner",
           "act": { "sub": "team-portal" } },
  "ark_claims": ["idp.clients.read", "idp.user.deactivate"]
}

  2. 2It calls an identity tool over MCP.

    To the agent this is any other tool. It sees the tools the gateway chose to offer, never the management API behind them.

    call
    tools/call  deactivate_user { "user_name": "bob@example.com" }

  3. 3The gateway checks, and writes it down first.

    Each tool names the claim it needs. The gateway is the only place that knows the agent, the person and the action together, so its record matters most.

    recorded
    {"tool": "deactivate_user", "user": "bob@example.com", "allowed": true,
 "for": "alice@example.com", "acting": ["planner", "team-portal"],
 "token_id": "zQuI6qGWm00i5NVWhcWUtw"}

  4. 4It fetches an operator token with its own credential.

    The machine credential lives in the gateway’s environment. Nothing the agent sends or receives contains it.

    request
    POST /ark_idp/oauth2/token

grant_type=client_credentials
client_id=ark_idp_machine&client_secret=•••
scope=client.register

  5. 5It calls the management API, and the change takes hold.

    Bob’s sessions and refresh tokens end at once, and the next agent that tries to carry him is refused. The gateway sends the ticket’s id as X-Correlation-ID, so ARK’s audit event can be matched to the gateway’s own line.

    recorded
    'bob@example.com' is now deactivated. Their sessions and refresh tokens
have been revoked; sign-ins are refused …

then, for Bob:
400 invalid_grant  the account subject_token belongs to has been deactivated.

  6. 6The short cut is closed.

    The management API answers the operator’s console session or the machine credential. The agent’s ticket and Alice’s own sign-in token both get the same answer.

    recorded
    GET /api/oauth/v1/client/list
Authorization: Bearer <the idp-mcp ticket>

401  the bearer token was refused - it must be issued by this server to the
     machine client, with the 'client.register' scope.

Inside the dashed line is the operator’s side. The agent’s ticket stops at the gateway.

The gateway, complete

Two tools, each with its own claim. This is the code the diagram was recorded from. ARK does not ship it: copy it, and add only the tools you need.

gateway.py · mcp 2.3.0, ark-oauth-client, httpx
import asyncio, json, os, httpx
from mcp.server.mcpserver import MCPServer
from mcp.server.mcpserver.exceptions import ToolError
from mcp.server.auth.provider import AccessToken
from mcp.server.auth.settings import AuthSettings
from mcp.server.auth.middleware.auth_context import get_access_token
from ark_oauth_client import ArkOAuthClient, agent_actors

IDP, TENANT = "https://idp.example.com", "acme"
URL = "https://identity-mcp.example.com/mcp"
ark = ArkOAuthClient(authority=f"{IDP}/{TENANT}", client_id="idp-mcp")
# The operator credential. It is read here, used here, and never sent to an agent.
machine = ArkOAuthClient(authority=f"{IDP}/ark_idp", client_id="ark_idp_machine",
                         client_secret=os.environ["ARK_MACHINE_SECRET"],

class ArkTokens:
    async def verify_token(self, token):
        try:
            p = await asyncio.to_thread(ark.verify_agent_token, token)
        except Exception:
            return None
        return AccessToken(token=token, client_id=p["client_id"], subject=p["sub"], claims=p,
                           scopes=p.get("scope", "").split(), expires_at=p["exp"])

def allow(claim: str, tool: str, **what):
    """Every tool starts here: hold the claim or stop, and leave a record either way."""
    t = get_access_token()
    ok = claim in t.claims.get("ark_claims", [])
    print(json.dumps({"tool": tool, **what, "allowed": ok, "for": t.subject,
                      "acting": agent_actors(t.claims), "token_id": t.claims["jti"]}), flush=True)
    if not ok:
        raise ToolError(f"{tool} needs {claim}")
    return t

def manage(t, method, path, body=None):
    token = machine.client_credentials(scopes=["client.register"]).access_token
    r = httpx.request(method, f"{IDP}/api/oauth/v1/{path}", json=body, timeout=30, headers={
        "Authorization": f"Bearer {token}",
        "X-Correlation-ID": t.claims["jti"]})   # ties the IdP's record to the line above
    r.raise_for_status()
    return r.json()

@mcp.tool()
def list_clients() -> list:
    """Applications registered in this tenant."""
    t = allow("idp.clients.read", "list_clients")
    rows = manage(t, "GET", "client/list")["data"]
    return [c["client_id"] for c in rows if c["tenant_id"] == TENANT]   # never another tenant's

@mcp.tool()
def deactivate_user(user_name: str) -> str:
    """Switch an account off. Accounts are server-wide: this applies in every tenant."""
    t = allow("idp.user.deactivate", "deactivate_user", user=user_name)
    return manage(t, "POST", "activation/user", {"user_name": user_name, "is_active": False})["msg"]

The gateway is as powerful as its credential

  • The machine credential administers every tenant. The gateway must filter to its own, as list_clients does.
  • Accounts are shared by all tenants. Switching one off switches it off everywhere.
  • Run it on the operator’s side of the network, with the secret from a vault.

Tools to leave out

  • Anything that edits a2a_callers, access mappings or grants. An agent that can edit the list can let itself in.
  • client/secret/reset: the answer contains a secret, and the agent would read it.
  • data/reset, data/import and deletes. Keep those for a person in the console.

Limits

What ARK does not do.

Read this before you commit. If one of these is a requirement for you, it is better to know now.

  • Browser sign-in from a third-party MCP client

    A desktop or editor MCP client that signs the user in itself gets a token for the whole tenant: ARK ignores resource on that path. A server that checks the audience, as it must, refuses it (tested). Sign users in to your own app, and let its back end exchange the token.

  • No MCP server in the box

    ARK issues and checks tickets. The gateway in flow 3 is code you run, and its tool list is yours to keep short.

  • It cannot judge intent

    An agent that is talked into misusing a right Alice really has will hold a valid ticket. ARK limits where it can go and what it can reach. Ask a person before anything destructive.

  • Bearer tickets

    Short-lived and tied to one door, but not to a key. There is no DPoP or mTLS binding, so whoever holds a ticket can use it at that door until it expires.

  • One tenant

    Agents call agents of the same tenant. There is no cross-tenant or cross-company ticket.

  • The operator consents, not Alice

    There is no screen asking her to let an agent act for her. Access is what the operator mapped and the list on each target.

  • Only people are carried down a chain

    When agents call each other in their own names, each call stands alone: the third agent sees the second, not the first.

  • ARK cannot see the call

    It knows that a ticket was printed, refused or asked about. What the agent then did is only in the receiver’s own record.

Questions reviewers ask

Before you say yes.

Why not simply pass Alice’s token to the agent?

Her token is good at every ordinary API of the tenant, so every agent in the chain, and everything those agents call, could use it anywhere as Alice. Exchanged tickets are good at one place, for minutes, and say which agent is acting.

Why not an API key per agent?

A key says which agent, and nothing about the person. It does not expire by itself, and whoever receives it can use it elsewhere. A key also leaves the receiver to work out what Alice may do, with no proof she was ever involved.

Does an agent ever see a password, a refresh token or a signing key?

No. Tickets come without a refresh token or an ID token. Alice’s refresh token stays in the portal’s session, and the signing key stays in ARK. An agent holds its own client secret or private key, and the tickets it is using.

What if an agent’s secret leaks?

The thief can ask for tickets in that agent’s name, at the doors that list it. They cannot carry a person without also holding a token of that person’s that was issued or addressed to that agent. Switch the client off and the next request is refused; tickets already out end within minutes. Registering the agent with private_key_jwt means there is no shared secret to leak.

Do I have to use the ARK client libraries?

No. It is standard OAuth: client credentials, token exchange (RFC 8693), resource indicators (RFC 8707) and JWT access tokens (RFC 9068). Flow 2 was recorded with the MCP SDK’s own client and no ARK code in it. The libraries save you the caching and the checks.

What happens while ARK is down?

Receivers verify against keys they have cached, so tickets already out keep working until they expire. No new ones can be printed. Keep more than one instance if that matters.

I do not use agents. Does this change anything for me?

With no caller listed, ARK issues no agent tickets. One request changes meaning: client_credentials with an audience other than the tenant’s used to have it ignored, and is now refused. Set Oidc:EnableA2A to false to remove the feature.
