Scale test — 21 November 2026

Can one ARK identity provider hold the sessions of 30,000 people who are all working at once? The provider was loaded with 30,000 accounts and driven through real sign-ins, single sign-on, token refreshes and UserInfo calls, first as released and then after the scale work described here. Every number below was measured; the release that carries the changes is the one after 2.3.0.

What was found

The provider's design was already sound for scale: sessions, codes and refresh tokens live in the database, so nothing ties a user to one machine. What held it back was how the hot paths were written.

Before

  • Every sign-in read the whole user table three times and the access-mapping table four. With 30,000 accounts the database read 4.9 billion rows without an index over the full test.
  • A confidential client paid a full password-grade hash on every token request.
  • A second instance behind the same address refused most sign-ins.
  • A sign-in storm slowed everyone who was already signed in.

After

  • The same lookups use indexes: 0.5 million rows read that way over the same test.
  • 6.6× the requests per second and 2.0× the sign-ins per second on one instance.
  • Two instances share one key ring through the database; none of 3,000 sign-ins failed.
  • During a storm, a refresh for a signed-in user takes 12.2 ms at the median, not 474 ms.

How it was tested

Data. 30,000 user accounts, each mapped to two applications (60,000 access mappings): one confidential web client authenticating with a client secret, one public client using PKCE alone. Passwords and the client secret are stored as the provider stores them, PBKDF2-SHA256 at 210,000 iterations.

Load. A purpose-built generator drove the provider over HTTP the way a browser and an application do: fetch the sign-in page, post the form with its anti-forgery token, grant consent on first use, exchange the code with PKCE, then read UserInfo. After sign-in, a steady mix of 40% single sign-on hops with the session cookie, 30% refresh-token rotations and 30% UserInfo calls. Each virtual user kept its own cookies and tokens.

Two kinds of run. Saturation runs push as hard as the server will take and report throughput. Paced runs hold a fixed rate, 400 operations a second, and report response times as a user would see them; 30,000 people refreshing hourly across a few applications and moving between them produce well under that.

One combined run. The last test in the results puts the pieces together, at one-third scale: two instances behind a load balancer over HTTPS, a database with network delay, people arriving while others work, every protocol flow in the mix, and sessions short enough to expire during the run.

Machine. One Apple M5 laptop (10 cores, 16 GB) ran everything: the provider on .NET 10, the database in Docker (PostgreSQL 16, MySQL 8.4) and the load generator. They compete for the same cores, so the absolute numbers are lower than a server with its own database would give. The comparison is like for like: same machine, same data, same test, restored to the same starting state before each run.

8. Everything together, at one-third scale: TLS, a load balancer, two instances and a database a network hop away

The tests above isolate one thing each. This one puts everything together. Two provider instances serve HTTPS behind an nginx load balancer; the database answers with 1 ms of added network delay each way; the audit trace is on. 10,000 people arrive at 50 a second while those already in keep working, each as busy as in the 30,000-user tests (133 operations a second with everyone in). The work now includes pushed authorization requests, the device flow, sign-out with back-channel logout to the application, and the legacy v1 flow. Sessions last four minutes, so the first arrivals' sessions run out before the end and those people sign in again; the purge runs every minute. Each instance may hash three passwords at once.

Why one-third scale. This topology was first run with all 30,000 users. That run is not reported: the load balancer in the test rig began refusing connections in the third minute (its upstream list included an address nothing listened on, and it takes an instance out of rotation after one failed connection), and the laptop, hosting two instances, the database, the load balancer and a TLS load generator on ten cores, did not recover its footing afterwards. 29,056 of the 30,000 people had still signed in by the fifth minute, the 1,155 failed requests were refused by the load balancer, and the provider logged no errors. The laptop was on battery with too little left to repeat it at full size, so the corrected rig was run at a size the machine can host. Response times are higher than in the earlier sections because every database round trip now costs about 2 ms on the wire and every request crosses the load balancer. That is the shape to expect in production.

One thing in this run is not explained. The medians and 95th percentiles above are what a user would see almost all the time, but the 99th percentiles are seconds, and they come from a single pause of about six seconds in the third minute, while people were still arriving. It hit every kind of request at once, including pages that never touch the database, produced no errors, and did not recur in the four minutes that followed. Nothing like it appears in sections 1 to 4, where one instance carried more load over plain HTTP: there the slowest refresh of the whole 30,000-user run took 30.6 ms. That points at something this rig adds — TLS connection set-up on macOS, Docker's port forwarding, or the laptop itself at 12% battery — but it was not established which, and until it is reproduced or ruled out on real hardware it should be treated as open.

What changed

Nothing a client application sees: endpoints, tokens, discovery and configuration are as in 2.3.0.

  • Lookups use indexes

    Accounts, access mappings and lockout counters were found by comparing lower-cased text, which no ordinary index can serve. They are now looked up by the stored value first, with an index on the lower-cased form for anything stored in another case.

  • Missing indexes are added to existing databases

    On its first start the new build creates the indexes the session, refresh-token and purge paths need. It never adds a unique index and never fails start-up over one.

  • Client secrets are verified once, then remembered briefly

    Only a correct secret is remembered, as a keyed digest held in memory for five minutes. A wrong secret costs what it always did, and replacing a secret takes effect at once.

  • Rarely changing rows are held for 30 seconds

    Tenants, clients, scopes and the signing key. A change made on an instance applies there immediately and on the others within the 30 seconds. Nothing about a user is held: accounts, access and sessions are read on every request.

  • Signing keys are loaded once

    Each token used to import the private key afresh, twice per response, and never release it.

  • Password hashing has a ceiling

    Half the cores by default. Sign-ins beyond that wait their turn without holding a thread; after 20 seconds the page says the server is busy rather than hanging.

  • One key ring for every instance

    The keys protecting the sign-in form and the console cookie are kept in the provider's database on PostgreSQL and MySQL, so any instance can read what another wrote.

  • Housekeeping keeps tables small

    The hourly purge now also removes refresh tokens whose session has ended, and can trim the audit trail. Ending a session, a user or a client is one statement instead of loading every row.

  • Failed sign-ins are counted exactly

    Simultaneous wrong guesses at one account used to be counted as one or two. Five at once are now counted as five, so the lockout engages when it should.

Behaviour checked after the changes

Speed that changes what the provider does would be a regression. The same 48 checks pass on PostgreSQL and on MySQL.

Sign-in and sessions

  • Login identifiers match whatever their case.
  • Wrong password and unknown user give the same message.
  • Lockout after five failures, cleared by a good sign-in.
  • Single sign-on reuses the session, and refuses an application the user has no access to.
  • Sign-out ends the session and its refresh tokens.

Tokens, clients and operators

  • Refresh tokens rotate; replaying a spent one revokes the family.
  • A wrong client secret is refused; a new secret retires the old one on the next request.
  • Deactivating a user or a client takes effect on the next request.
  • A signing key rotated elsewhere is published at once and adopted within 30 seconds; older tokens still validate.
  • The audit trail is written, including error rows that were previously lost.

For operators

To run 30,000 users

  1. Use PostgreSQL or MySQL. SQLite is for a single small instance.
  2. Upgrade and let the first start build its indexes. On a large database that start takes a little longer.
  3. Run at least two instances for availability. They need the shared database and the same BaseUrl, nothing else; no session affinity.
  4. Size for sign-in, the one expensive request: about 25 sign-ins a second per core given to hashing. 30,000 people arriving over fifteen minutes is 33 a second.
  5. If EnableLogTrace stays on, set Oidc:AuditRetentionDays.

What this test does not show

Everything ran on one laptop. The combined run adds TLS, a load balancer, a second instance and network delay to the database, but the instances, the database and the load generator still share ten cores, the database serves nothing else, and that run is at one-third of the 30,000 users: the production-shaped deployment has not been measured at full size. The longest run is seven minutes with sessions shortened to match, which shows sessions expiring, people signing in again and the purge keeping up, but it is not a soak: a leak that takes hours to show would not appear here. That run also contains one unexplained six-second pause, described with its results. The laptop was on battery, which ruled out a longer or larger run, and chasing the pause, on the day. SQL Server was not tested. Treat the figures as evidence that the provider's own code is no longer the limit, and run the same test, for a full day, on the hardware you deploy to; the generator and its instructions are in scripts/loadtest.
