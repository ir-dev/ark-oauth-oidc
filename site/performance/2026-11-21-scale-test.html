Scale test — 21 November 2026

Can one ARK identity provider hold the sessions of 30,000 people who are all working at once? What was found

The provider's design was already sound for scale: sessions, codes and refresh tokens live in the database, so nothing ties a user to one machine. What held it back was how the hot paths were written.

Before

  • Every sign-in read the whole user table three times and the access-mapping table four. With 30,000 accounts the database read 4.9 billion rows without an index over the full test.
  • A confidential client paid a full password-grade hash on every token request.
  • A second instance behind the same address refused most sign-ins.
  • A sign-in storm slowed everyone who was already signed in.

After

  • The same lookups use indexes: 0.5 million rows read that way over the same test.
  • 6.6× the requests per second and 2.0× the sign-ins per second on one instance.
  • Two instances behind a load balancer carried all 30,000 users through 804,332 requests in 25 minutes with 0 errors (before: 303 of 400 sign-ins refused with two instances).
  • During a storm, a refresh for a signed-in user takes 12.2 ms at the median, not 474 ms.

Data, load generator and method

Data. 30,000 user accounts, each mapped to the test applications, in the provider's own schema; on PostgreSQL the accounts and their mappings occupy about 52 MB. Passwords and the client secret are stored as the provider stores them. Before each run the database was restored to the same starting state.

Load generator. A .NET 10 console program in this repository (scripts/loadtest), on the same machine. It drives the provider over HTTP exactly as a browser and an application do: fetch the sign-in page, post the form with its anti-forgery token, grant consent on first use, exchange the code with PKCE, read UserInfo, rotate refresh tokens, and so on. Each virtual user keeps its own cookies and tokens. There is no think time: a "concurrent user" here is a user with a request always in flight, which is far busier than a person.

Kinds of run. Saturation: a fixed number of users, each sending the next request as soon as the last returns; reports throughput. Paced: a fixed number of operations a second regardless of how the provider responds; reports response times as a user would see them. Step load: a number of users signing in at once, raised in steps.

Measurement. Response time is measured in the generator, from sending a request to having read the whole response. Percentiles are nearest-rank over every sample in the phase. A rate is completed operations divided by elapsed time. An error is any response other than the one the flow expects. Provider processor time and memory come from the operating system; database figures from PostgreSQL's own statistics.

Which build. Sections 1 to 7, and the one-third-scale run in section 8, were measured before three late changes that make the upgrade invisible to people using the provider (existing keys carried into the shared key ring, client records re-read before any refusal, and no sign-in turned away unless an operator asks for that). None of the three is on a path those sections measure. The behaviour checks, the full run in section 8, section 9 and the unit costs ran on the final build.

Getting there: the first attempts on this topology

The run above was the third attempt at this topology, and what the first two showed is worth keeping. In them the instances terminated TLS themselves, with nginx passing the encrypted connection straight through. The first, at full size, was spoiled by a load-balancer misconfiguration in the rig. The second, below, ran at one-third scale: 10,000 people arriving at 50 a second, each as busy as in the 30,000-user tests, sessions lasting four minutes so that they expire within the run, the purge running every minute.

Why one-third scale. A laptop has to host everything here: two instances, the database in a virtual machine, the load balancer, and a load generator. At the full 30,000 with arrivals compressed to 100 a second it runs out of processor, and the numbers stop describing the provider (the generator's own timers ran up to 0.7 s late). At one-third scale, with each person as busy as in the 30,000-user tests, it does not.

Response times are higher than in the earlier sections because every database round trip now costs about 2 ms on the wire and every request crosses the load balancer. That is the shape to expect in production.

The pause in minute 3, and its cause. The medians and 95th percentiles above are what a user sees almost all the time, but the 99th percentiles are seconds. They come from one pause of about six seconds in the third minute, which hit every kind of request at once and produced no errors. It was traced. During such a pause the database logged no slow statement, and a dump of the provider's threads showed every worker thread inside the TLS handshake that .NET performs through macOS's security framework, which blocks the thread it runs on. A burst of new TLS connections therefore stalls a provider that terminates TLS itself on macOS. Providers are deployed on Linux, normally behind a load balancer or an App Service front end that terminates TLS, so the rig was rebuilt that way and the test run at the full 30,000: the result at the top of this section, with no pause.

9. Step load: sign-ins from 100 to 10,000 at once

How does sign-in behave as more and more people try at the same moment? One instance of the current build with default settings, PostgreSQL, the 30,000 accounts. 100 people sign in at once and keep doing so for 30 seconds, each as a new browser going through the whole flow (sign-in page, form with its anti-forgery token, code, token exchange with PKCE and the client secret); then 100 more join, and so on in steps of 100 up to 2,000, then in steps of 1,000 up to 10,000. Consent had been granted beforehand, as it has for a returning user. From 3,000 upwards each level's newcomers join over ten seconds instead of in the same instant, because an operating system queues only so many new connections at once, and the generator waits up to five minutes for a response.

Reading it. 204,254 sign-ins, 0 errors, nobody turned away at any level. The rate stays between 125 and 175 a second throughout: it is set by password hashing, which this machine's default allows on five cores at a time, and nothing else gives way first. So the time a person waits is the size of the crowd divided by that rate: about 595 ms at 100 at once, 11.59 s at 2,000, 42.23 s at 10,000. By default a sign-in waits its turn however long that takes; an operator who would rather shed load can set Oidc:MaxPasswordHashWaitSeconds.

The two columns for single requests show how the rest of the provider fares while the crowd waits. Up to 5,000 at once, the sign-in page (no hashing, no database) still answers in a few milliseconds and the token exchange, with its five database round trips, in about 8 ms: the queue is in front of the hashing and nowhere else. From 6,000 the page slows to hundreds of milliseconds and the generator's own timers run late, which says the laptop as a whole is short of processor at that size, so the last levels understate what the provider would do with the generator on a machine of its own. About six cores are busy at every level, five hashing and one for everything else. Provider memory rises with the number of requests held in flight. The connection pool sits at its ceiling of 100 throughout and is not what limits the rate. Among the first twenty levels, the two slower ones, 1,000 and 1,800, each coincide with a PostgreSQL checkpoint completing on this laptop's virtual disk. To sign people in faster, add cores or instances: the rate scales with the cores given to hashing.

Why it stops at 10,000. One machine can hold only about 16,000 connections to another address on itself, so a single load generator on the same laptop cannot hold 30,000 sign-ins open at once. The relationship is a straight line through every level measured, so the wait at any crowd size is that size divided by the rate. 30,000 people who are signed in and working, as opposed to 30,000 pressing "sign in" in the same second, is what sections 1, 2 and 8 measure.

What changed

Nothing a client application sees: endpoints, tokens, discovery and configuration are as in 2.3.0.

  • Lookups use indexes

    Accounts, access mappings and lockout counters were found by comparing lower-cased text, which no ordinary index can serve. They are now looked up by the stored value first, with an index on the lower-cased form for anything stored in another case.

  • Missing indexes are added to existing databases

    On its first start the new build creates the indexes the session, refresh-token and purge paths need. It never adds a unique index and never fails start-up over one.

  • Client secrets are verified once, then remembered briefly

    Only a correct secret is remembered, as a keyed digest held in memory for five minutes. A wrong secret costs what it always did, and replacing a secret takes effect at once.

  • Rarely changing rows are held for 30 seconds

    Tenants, clients, scopes and the signing key. A change made on an instance applies there immediately. No request is refused on a held copy: the record is read again first, so a new secret, redirect address or scope works everywhere at once, and only a change that takes something away needs up to the 30 seconds to reach other instances. Nothing about a user is held: accounts, access and sessions are read on every request.

  • Signing keys are loaded once

    Each token used to import the private key afresh, twice per response, and never release it.

  • Password hashing has a ceiling

    Half the cores by default. Sign-ins beyond that wait their turn without holding a thread. Nobody is turned away unless an operator sets a waiting limit.

  • One key ring for every instance

    The keys protecting the sign-in form and the console cookie are kept in the provider's database on PostgreSQL and MySQL, so any instance can read what another wrote. The keys already in use are carried across, so the upgrade signs nobody out.

  • Housekeeping keeps tables small

    The hourly purge now also removes refresh tokens whose session has ended, and can trim the audit trail. Ending a session, a user or a client is one statement instead of loading every row.

  • Failed sign-ins are counted exactly

    Simultaneous wrong guesses at one account used to be counted as one or two. Five at once are now counted as five, so the lockout engages when it should.

Behaviour checked after the changes

Speed that changes what the provider does would be a regression. 48 checks pass on PostgreSQL, MySQL and SQLite, and 20 more cover the admin console's own sign-in and two instances sharing one database. A sign-in form drawn by version 2.3.0 is accepted by the new build after an upgrade in place.

Sign-in and sessions

  • Login identifiers match whatever their case.
  • Wrong password and unknown user give the same message.
  • Lockout after five failures, cleared by a good sign-in.
  • Single sign-on reuses the session, and refuses an application the user has no access to.
  • Sign-out ends the session and its refresh tokens.

Tokens, clients and operators

  • Refresh tokens rotate; replaying a spent one revokes the family.
  • A wrong client secret is refused; a new secret retires the old one on the next request.
  • Deactivating a user or a client takes effect on the next request.
  • A signing key rotated elsewhere is published at once and adopted within 30 seconds; older tokens still validate.
  • The audit trail is written, including error rows that were previously lost.
  • A secret regenerated, a redirect address or scope added, or a client reactivated on one instance works on the other on the next request.
  • The admin console signs in, lists clients and exports data; the export never contains the key ring.

How much processor: sign-in sets it

Sign-ins per second = cores hashing at once × hashes per core per second. Measured here: 159 sign-ins a second sustained over 204,254 sign-ins with five cores hashing, which is 32 a second per hashing core, on a processor where some of those cores are the slow kind. On cloud virtual CPUs measure it; until then plan on 25 a second per hashing core. By default half the instance's cores hash.

While more people are trying to sign in than that, they queue, and the wait is the size of the queue divided by the rate: section 9 shows 595 ms with 100 signing in at once and 42.23 s with 10,000. Nobody was refused at any size.

How many instances

For everything except sign-in, one instance has room to spare: 30,000 people each refreshing tokens hourly and moving between a few applications produce about 552 requests a second in this report's model, and one instance sustained 2,308 on this laptop while sharing it with the database and the load generator (section 3). Run at least two for availability, not for capacity. Two instances behind one address were tested: every sign-in succeeded, sessions and tokens issued by one were honoured by the other, and no session affinity was needed (sections 5 and 8). In section 8, two instances with three hashing slots each carried all 30,000 people, arriving at 33 a second and then working at 400 operations a second, with every response-time median under 76.1 ms.

Where TLS ends

Terminate TLS at the load balancer or platform front end, and let the provider receive plain HTTP on a private network, with BaseUrl set to the public address. That is how Azure App Service and most container platforms already work. It is the configuration that ran cleanly here. Terminating TLS inside the provider was only tested on macOS, where it stalls under bursts of new connections for a reason specific to macOS (section 8); Kestrel terminating TLS on Linux was not tested.

Database sizing

PlacementSame region and network as the provider. Each millisecond of round trip adds 7 ms to a refresh and 11 ms to a sign-on hop (table above).
ConnectionsEach instance holds up to 100 by default (Maximum Pool Size). The pools filled during sign-in bursts and were never what limited throughput. Give the database at least instances × pool size, plus headroom.
WritesA sign-in writes a session, a record of the application joined, an authorization code and a refresh token. A refresh writes one row and updates one. With the audit trace on, add about three rows per sign-in.
DiskSynchronous-write speed matters more than size. On this laptop's virtual disk, each five-minute PostgreSQL checkpoint cost up to a quarter of the sign-in rate for part of a minute (section 9, the levels at 1,000 and 1,800). Expect that effect to be smaller on server storage, and watch for it.
SizeSmall. 30,000 accounts with three application mappings each: about 52 MB. After 30,000 sign-ins the whole database was 112 MB. The hourly purge removes expired sessions with their tokens, so the grant tables track the signed-in population, not history.

For operators

To run 30,000 users

  1. Use PostgreSQL or MySQL. SQLite is for a single small instance.
  2. Upgrade and let the first start build its indexes. On a large database that start takes a little longer.

  4. Size for sign-in, the one expensive request: about 25 sign-ins a second per core given to hashing. 30,000 people arriving over fifteen minutes is 33 a second.

What this test does not show

Everything ran on one laptop: the instances, the database and the load generator share ten cores, and the database serves nothing else. The production-shaped test ran at the full 30,000 for 25 minutes with people arriving at the realistic rate of 33 a second; when arrivals were compressed to 100 a second on that topology the laptop itself ran out of processor, so its headroom for a sharper peak is known only for a single instance (sections 4 and 9). No run is longer than 25 minutes, with sessions shortened to match: that shows sessions expiring, people signing in again and the purge keeping up, but it is not a soak, and a leak that takes hours to show would not appear here. Terminating TLS inside the provider was tested only on macOS. SQL Server was not tested. Treat the figures as evidence that the provider's own code is no longer the limit, and run the same test, for a full day, on the hardware you deploy to; the generator and its instructions are in scripts/loadtest.
