WHAT SHIPS IN THIS RELEASE
--------------------------------------------------------------------------------
  Ark.oAuth.Oidc     2.0.2  ->  2.0.3    the IdP / provider
  Ark.oAuth.Client   2.0.2  ->  2.0.3    the ASP.NET Core client

  Both are at 2.0.2 on nuget.org (confirmed against the flat container on
  2026-08-29; 2.0.0, 2.0.1 and 2.0.2 are live, nothing higher). 2.1.x was
  written into the provider csproj once and never published -- it does not
  exist publicly and nothing in the tree points at it any more.

  THE PROVIDER IS THE RELEASE. It gains OIDC Back-Channel Logout 1.0, sign-out
  that covers every session in the browser rather than the one the cookie
  names, the registration metadata for both (dynamic registration, the
  provisioning API and the console's client editor), corrected discovery
  (backchannel_logout_* true, frontchannel_logout_* now false instead of
  advertising an endpoint that does not exist), and schema script 00005.

  THE CLIENT IS A VERSION ALIGNMENT. No source file under Ark.oAuth.Client has
  changed since the 2.0.2 release commit -- `git diff <2.0.2 tag or commit>..HEAD
  -- Ark.oAuth.Oidc/Ark.oAuth.Client` is empty. It is rebuilt and pushed only so
  the two halves carry the same number, which is what every doc and sample here
  assumes. Skipping it is defensible; if you do, say so, because STEP 7 then has
  one package to confirm and not two.

  ONE CHANGE THAT IS NOT ADDITIVE, and the reason to read the diff before
  pushing: the provider's dependency list is now what it uses. Ark.EfCore,
  Azure.Identity and BouncyCastle are gone, and Microsoft.EntityFrameworkCore
  9.0.19 + the Sqlite / MySQL / PostgreSQL providers are named directly. What
  2.0.2 published was:

    Ark.EfCore 0.0.1.3, Azure.Identity 1.13.2, BouncyCastle.Cryptography 2.5.1,
    Microsoft.IdentityModel.JsonWebTokens 8.8.0,
    System.IdentityModel.Tokens.Jwt 8.8.0, ark.net.util 1.0.4.14

  A consumer that was reaching those three transitively -- most likely EF Core
  8.0.x, or Microsoft.Data.SqlClient through Ark.EfCore -- loses them on
  upgrade and has to reference them itself. Nothing in this package used them.
  Verify the shipped list in STEP 5c rather than trusting the csproj.

  Not part of this release: ark_oauth_client_nodejs (npm "ark-oauth-client",
  still at 2.0.1). It is published with npm, not nuget, and is left untouched.
  It speaks the protocol as a relying party and needs nothing from 2.0.3 unless
  you want it to receive logout tokens. Bump and publish it separately.

  NOTE ON THE NUMBER: 2.0.3 is a patch version carrying an additive feature and
  a schema script, which SemVer would call a minor bump -- the same call as
  2.0.2. It publishes and resolves fine (2.0.3 > 2.0.2, so it becomes latest)
  and no consumer is stranded, because 2.1.x has never existed publicly.

 STEP 6  —  PUSH TO NUGET.ORG
================================================================================

  cd /Users/Immanuel.Raj/Immi/git_src/ark-oauth-oidc/Ark.oAuth.Oidc

  # The provider
  dotnet nuget push Ark.oAuth.Oidc/bin/Release/Ark.oAuth.Oidc.2.0.3.nupkg \
    --api-key "$NUGET_API_KEY" \
    --source https://api.nuget.org/v3/index.json \
    --skip-duplicate

  # The client
  dotnet nuget push Ark.oAuth.Client/bin/Release/Ark.oAuth.Client.2.0.3.nupkg \
    --api-key "$NUGET_API_KEY" \
    --source https://api.nuget.org/v3/index.json \
    --skip-duplicate

  Notes on these two commands:

  * SYMBOLS GO AUTOMATICALLY. Pushing X.nupkg also pushes X.snupkg when it sits
    in the same directory. Do not push the .snupkg as a separate command -- that
    is what produces a confusing 409 on the symbol package. Pass --no-symbols to
    suppress it deliberately.

  * --skip-duplicate turns "this version already exists" (HTTP 409) into a
    warning instead of a failed command. Useful when re-running after a partial
    push; it does NOT overwrite anything.

  * Point --source at the v3 index URL, not at the "nuget.org" source name, so
    the push cannot be diverted by the repo-local nuget.config.

  * Expect "Your package was pushed." Indexing and validation on nuget.org then
    take a few minutes to about 15 before the version is installable, and the
    symbol package is validated separately and can lag further.

================================================================================
 IF SOMETHING GOES WRONG
================================================================================

  A pushed version can never be replaced. Options, in order of preference:

  1. Unlist it (hides it from search and from the version dropdown; existing
     consumers who pin it can still restore it):
       dotnet nuget delete Ark.oAuth.Oidc 2.0.3 \
         --api-key "$NUGET_API_KEY" \
         --source https://api.nuget.org/v3/index.json \
         --non-interactive
     On nuget.org "delete" IS unlist -- the bits stay available. Confirm on the
     package page that it shows as unlisted.

  2. Ship 2.0.4. This is the normal fix. Bump both csproj version triples,
     add a notes entry, and repeat from STEP 1.

  3. Genuine hard delete (leaked secret, license problem) requires contacting
     nuget.org support; it is not something this CLI can do.

  Common failures:

  * 403 Forbidden          key is expired, not push-scoped, or its glob does not
                           cover the package id. Regenerate on nuget.org.
  * 409 Conflict           that version already exists. Bump; do not fight it.
  * NU5046 icon missing    the icon must be packed with an EMPTY PackagePath.
                           PackagePath="\" is taken literally on macOS and lands
                           the file in a directory named "\". Both csproj files
                           already do this correctly -- do not "fix" them.
  * NU1701 / graph errors  Microsoft.IdentityModel.* must stay aligned at 8.8.0
                           across JsonWebTokens, Protocols.OpenIdConnect and
                           System.IdentityModel.Tokens.Jwt. A split graph builds
                           fine and then fails at the first OIDC challenge with
                           "Cannot redirect to the authorization endpoint".
