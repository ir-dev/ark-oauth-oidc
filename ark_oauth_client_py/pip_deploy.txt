  The Python port of Ark.oAuth.Client, numbered to match the NuGet package it

 READ THIS BEFORE YOU PASTE A TOKEN ANYWHERE
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
  THIS FILE IS IN A PUBLIC GITHUB REPOSITORY. So is everything beside it.

  A PyPI API token is a live credential that can publish code under your name
  to a registry other people install from. Do not write one into this file, an
  example, a test, a commit message, or a shell script in the tree. This repo
  has already had one live key purged from its history (2026-08-19); a second
  incident costs the same day of work plus every downstream install that ran in
  between.

  Tokens belong in exactly one of:
    - an environment variable set in your shell, not in a file that is tracked
    - ~/.pypirc, which is OUTSIDE the repo (chmod 600)
    - the macOS keychain, via keyring
    - GitHub Actions Trusted Publishing, where there is no token at all
      -- the best answer for a public repo, see APPENDIX B

  If you ever paste one and think better of it: revoke it at
  https://pypi.org/manage/account/token/ FIRST, then clean up. Revoking is
  instant and free; rewriting history is neither.

CHOOSING A PUBLISHER  --  twine is no longer the only option
--------------------------------------------------------------------------------
  Both paths below were run against this package on this machine. They produce
  byte-for-byte equivalent artifacts (verified: identical 33-entry file lists
  in the wheel, both PASS twine check), so this is a choice about ergonomics
  and supply-chain features, not about output.

  PATH A -- uv          RECOMMENDED HERE. Already installed: uv 0.9.26.
    + One tool builds and publishes; no release venv to create at all.
    + `uv build` took 0.9s here. `python -m build` takes ~10s, because it
      creates an isolated venv and downloads hatchling into it every time.
    + `uv publish --dry-run` rehearses the upload without sending anything.
    + Uploads PEP 740 attestations by default under Trusted Publishing --
      signed provenance tying the artifact to the workflow that built it.
      twine does not do this.
    + Reads the same pyproject.toml. No project change required; the build
      backend stays hatchling either way.
    - Newer, and one more thing to have installed. Not a problem here.

  PATH B -- build + twine     The long-standing default.
    + Universally documented; every PyPI answer online assumes it.
    + `twine check` renders the README the way PyPI will, which uv has no
      direct equivalent for. Worth keeping in the loop even on Path A.
    - Two tools, a venv to hold them, and a slower build.

  NOT USED HERE, and why: hatch, flit, poetry and pdm each bundle their own
  publish command, but each also wants to own the project's build and
  dependency configuration. This package uses plain hatchling through
  pyproject.toml with no tool-specific sections, which keeps it buildable by
  anything. Adopting one of those to get its `publish` verb would be a
  project-wide commitment for a step that takes one command either way. None
  of them is installed on this machine.

  MIXING IS FINE and is what the steps below actually do: build with uv,
  README-check with twine, upload with either.

================================================================================
 STEP 3  --  CREDENTIALS  (pick ONE; do not do both)
================================================================================

  Skip entirely if you are using Trusted Publishing (APPENDIX B).

  OPTION A -- environment variables. Nothing on disk. Gone when the shell
  closes, which is the point. Note the leading space on each line: with
  HIST_IGNORE_SPACE / `setopt histignorespace` in zsh that keeps the token out
  of ~/.zsh_history. Verify your shell honours it before relying on it.

     For uv:
         export UV_PUBLISH_TOKEN='pypi-AgEIcHlwaS5vcmc...'

     For twine:
         export TWINE_USERNAME=__token__
         export TWINE_PASSWORD='pypi-AgEIcHlwaS5vcmc...'

     TWINE_USERNAME is the literal string __token__ -- not your account name.
     uv's --token flag handles that for you.

  OPTION B -- ~/.pypirc. Outside the repo, so it is not a commit risk, but it
  is plaintext on disk until you remove it. chmod 600 is not optional. Read by
  twine; uv does not read it, so pair this with OPTION A or C for Path A.

         cat > ~/.pypirc <<'EOF'
         [distutils]
         index-servers =
             pypi
             testpypi

         [pypi]
         username = __token__
         password = pypi-REPLACE-ME

         [testpypi]
         repository = https://test.pypi.org/legacy/
         username = __token__
         password = pypi-REPLACE-ME-TEST
         EOF
         chmod 600 ~/.pypirc

  OPTION C -- macOS keychain. Prompts once, stores in the keychain, nothing in
  a file at all. Both tools can read it.

         uvx keyring set https://upload.pypi.org/legacy/ __token__
         uvx keyring set https://test.pypi.org/legacy/  __token__

     Then: uv publish --keyring-provider subprocess -u __token__
       or: twine upload -u __token__ dist/*

================================================================================
 STEP 5  --  VERIFY THE ARTIFACTS BEFORE ANYTHING LEAVES THIS MACHINE
================================================================================

  Everything here is cheap and local. The upload is the irreversible step, so
  do all of it first.

  a. Metadata and README rendering. A README that does not render leaves the
     project page blank on PyPI and cannot be fixed without a new version.
     This is twine's one irreplaceable job -- run it even on Path A, where
     uvx fetches it on demand and leaves nothing installed:

        uvx twine check dist/*                       # Path A
        ./.venv-release/bin/twine check dist/*       # Path B

     Expect: PASSED for both files.

  b. What is actually inside the wheel -- 30 package files plus 3 dist-info
     entries. Confirm py.typed is present and that no test, example, venv or
     .env crept in.

        python3 -m zipfile -l dist/ark_oauth_client-2.0.4-py3-none-any.whl

  c. What is inside the sdist. Tests and examples ARE included here by design
     (see [tool.hatch.build.targets.sdist] in pyproject.toml) so the package
     can be rebuilt and re-tested from source.

        tar -tzf dist/ark_oauth_client-2.0.4.tar.gz

  d. Nothing secret shipped. Should print "clean":

        tar -xzOf dist/ark_oauth_client-2.0.4.tar.gz \
          | grep -nE 'pypi-Ag|BEGIN [A-Z ]*PRIVATE KEY|client_secret *= *"[^"]' \
          || echo "clean"

  e. Install the built wheel into a THROWAWAY environment and run the suite
     against the INSTALLED package -- not the source tree. This is the check
     that catches a packaging mistake an editable install hides: a module left
     out of the wheel, a missing __init__.py, py.typed not shipped.

     Path A, in one command, nothing left behind:

        rm -rf /tmp/arkcheck && mkdir /tmp/arkcheck && cp -r tests /tmp/arkcheck/ \
          && (cd /tmp/arkcheck && uv run --no-project \
                --with "$OLDPWD/dist/ark_oauth_client-2.0.4-py3-none-any.whl[flask]" \
                --with pytest -- pytest tests -q)

     Path B:

        rm -rf /tmp/ark-verify && python3 -m venv /tmp/ark-verify
        /tmp/ark-verify/bin/pip install "dist/ark_oauth_client-2.0.4-py3-none-any.whl[flask]" pytest
        rm -rf /tmp/arkcheck && mkdir /tmp/arkcheck && cp -r tests /tmp/arkcheck/ \
          && (cd /tmp/arkcheck && /tmp/ark-verify/bin/python -m pytest tests -q)

     Verified 2026-08-29: 129 passed against the installed wheel.

  f. Rehearse the upload itself. Path A only, and genuinely worth it -- it
     validates the files against the real endpoint and sends nothing:

        uv publish --dry-run --publish-url https://test.pypi.org/legacy/ dist/*

     Outside CI this also prints "Trusted publishing failed / No OIDC token
     discovered". That is EXPECTED on a laptop -- it means uv looked for a CI
     identity and did not find one. The dry run still exits 0.

  g. Record the hashes, so you can prove later that what is on PyPI is what you
     built here:

        shasum -a 256 dist/*

     2.0.4 as built on 2026-08-29:
       48fd97cdc378db90a0c7328ddbc2461232eb9deef2958ea168e6ec849df9097d  ...-py3-none-any.whl
       7aba82c66ff1a50de8d3732bda9687a02aa5e7104f3dd5ee2439a76e106bb2ac  ...tar.gz

     These will NOT match if you rebuild -- the sdist embeds timestamps. Take
     the hashes of the artifacts you are actually about to upload.

  classifiers and the project links (Homepage / Repository / Issues /

================================================================================
 IF SOMETHING GOES WRONG
================================================================================

  400  File already exists
        That exact version is on PyPI already. Versions are immutable. Bump and
        rebuild -- there is no overwrite. twine --skip-existing and uv
        --check-url only make a re-run quiet; they do not replace anything.

  403  Invalid or non-existent authentication information
        With twine, TWINE_USERNAME must be the literal __token__, not your
        account name. The token must be for the right registry -- a PyPI token
        is rejected by TestPyPI and vice versa. Check it has not been revoked.

  403  The user ... isn't allowed to upload to project ...
        Somebody else owns the name now. Nothing to do but rename: change
        `name` in pyproject.toml (the import package `ark_oauth_client` can
        stay as it is) and rebuild.

  400  The description failed to render
        `twine check` catches this before upload -- run STEP 5a. README.md is
        served as text/markdown via readme = "README.md" in pyproject.toml.

  "Trusted publishing failed / No OIDC token discovered"  (uv, on a laptop)
        Expected outside CI. Supply --token, or set UV_PUBLISH_TOKEN. To stop
        uv probing at all: --trusted-publishing never

  Invalid distribution metadata / unknown Metadata-Version
        twine is older than the metadata the build backend emitted. Upgrade it:
        pip install --upgrade twine   (or just use uvx twine, always current)

  A wrong or broken release is already public
        Yank rather than delete. Yanking leaves it installable for anyone who
        pinned it exactly, but stops new resolutions picking it up -- deleting
        breaks builds that already reference it and still does not free the
        version number:
        https://pypi.org/manage/project/ark-oauth-client/releases/

  Token committed by accident
        Revoke at https://pypi.org/manage/account/token/ FIRST. Then purge.
        See the note at the top of this file -- it has happened here before.

================================================================================
 APPENDIX B  --  TRUSTED PUBLISHING  (no token at all -- best for a public repo)
================================================================================

  GitHub Actions authenticates to PyPI with a short-lived OIDC identity. There
  is no token to store, leak, rotate or commit, and PyPI attaches signed PEP
  740 attestations proving which workflow built the artifact. Given this repo
  is public and has already had one credential incident, this is the option to
  move to.

  1. On PyPI: Your projects -> ark-oauth-client -> Publishing -> Add a new
     pending/trusted publisher.
        Owner:              ir-dev
        Repository:         ark-oauth-oidc
        Workflow filename:  publish-python.yml
        Environment:        pypi
     (Before the first release the project does not exist yet -- use "pending
     publisher" under https://pypi.org/manage/account/publishing/ instead.)

  2. Commit .github/workflows/publish-python.yml:

        name: Publish ark-oauth-client to PyPI
        on:
          push:
            tags: ["py-v*"]
          workflow_dispatch:

        jobs:
          release:
            runs-on: ubuntu-latest
            environment: pypi
            permissions:
              id-token: write          # REQUIRED: mints the OIDC token
            steps:
              - uses: actions/checkout@v4
              - uses: astral-sh/setup-uv@v5
              - name: Test
                working-directory: ark_oauth_client_py
                run: uv run --extra dev pytest -q
              - name: Build
                working-directory: ark_oauth_client_py
                run: uv build
              - name: Check README renders
                working-directory: ark_oauth_client_py
                run: uvx twine check dist/*
              - name: Publish
                working-directory: ark_oauth_client_py
                run: uv publish dist/*      # no token: OIDC does it

  3. Release by tagging, which is STEP 9 doing double duty:

        git tag -a py-v2.0.5 -m "ark-oauth-client 2.0.5" && git push origin py-v2.0.5

  `permissions: id-token: write` is the line everyone forgets; without it the
  workflow cannot mint the OIDC token and uv falls back to looking for a
  password it does not have. The `environment:` also lets you require a manual
  approval on the GitHub side before anything is published.

  The equivalent with twine is `pypa/gh-action-pypi-publish@release/v1`, which
  works the same way and needs the same `id-token: write`.
